# Decisions

Deviations from, and resolutions of, the **BRD v1** and the **Engineering Build Guide**.
The BRD wins on scope; the Build Guide wins on how. Anything the two leave open, or that
could not be built as written, is recorded here so the code never silently drifts.

## Product decisions (product owner, 2026-09-15)

| ID | Decision | Notes |
|---|---|---|
| D-1 | Positions are ranked **within the arm** by default (3rd of 30 in JSS 1A). | School setting `positionScope`: `ARM` \| `CLASS`. |
| D-2 | Ties use **competition ranking** by default: 1, 2, 2, 4. | School setting `tieMode`: `COMPETITION` \| `DENSE` (1, 2, 2, 3). Satisfies FR-13.4 "configurable"; there is still exactly one ranking function, taking the mode as a parameter. |
| D-3 | An **empty score cell means "not entered yet"** and blocks *Mark complete*. | Absent students are recorded as `ABS` (`Score.isAbsent = true`, value 0). A typed 0 counts as 0. |
| D-4 | **One account per email**, unique across the platform. | Deviates from FR-7.2's "a person could hold accounts at multiple schools": they can, with a different email per school. Emails are stored lowercase. |
| D-5 | Parents get in by **email invite** by default; schools may also issue **printed access codes** to parents without email. | School setting `parentAccessCodes`. A code-only parent is a `User` with role `PARENT` and no email, linked to children the same way. Codes are stored hashed and shown once. |
| D-6 | Local development runs Postgres, Redis and Mailpit in **Docker Desktop**. | See S-8. |
| D-7 | **Frontend first** (2026-09-16): screens are built ahead of backend steps 3–7. | Login, invites and password reset use the real API. Everything else uses stand-in data served by MSW, shaped exactly like the API contract types in `packages/shared-types`. Each stand-in handler is deleted when its endpoint ships. Production builds never include stand-in data. Deviates from Guide §11's order; its precondition for UI work (tenant-isolation tests passing) is met. |
| D-8 | **One web app, one folder per portal**: `apps/web/src/portals/{teacher,admin,parent,super-admin}`. | One address and one login page that sends each person to their own portal. Portals are lazy-loaded, so a parent's phone never downloads admin or teacher code. Replaces Guide §2's `pages/<role>`. The teacher portal is built first. |
| D-9 | **Visual direction:** modern, smooth, simple and classy; purposeful animation, animated numbers and charts welcome; **no heavy divider lines**. | Anthropic's `frontend-design` skill (Apache-2.0) is installed in `.claude/skills/frontend-design` and guides UI work; the `dataviz` skill governs charts. See F-35. |
| D-10 | **Landing design: draft C (cinematic motion)**, built as a separate marketing site at `apps/site` (Vite, plain HTML/CSS/TypeScript, no framework). | Chosen on brand over draft A's scorecard, with conditions: the intro screen plays on a first visit only; the custom cursor appears only over buttons and links, and magnetic buttons stay; the page carries real photographs; every claim is checked against the BRD; sample content stays but is visibly marked. Webfonts (Outfit for display, Instrument Sans for reading, plus Inter Tight subset to the single ₦ glyph Outfit lacks) are allowed here and still banned in `apps/web` (Guide §6): the site is read once over data, the app is used all day. |
| D-11 | **Motion has a floor.** Every effect degrades to a plain, complete page. | The intro is skipped on a return visit and under reduced motion; the pinned horizontal tour becomes a vertical stack on phones and under reduced motion; reveals, counters, parallax and the cursor all no-op under reduced motion. Checked by screenshot at 1440 and 390, light and dark, plus a reduced-motion pass. |
| D-12 | **The trial-request form is the only way in from the site**, and posts to `POST /api/v1/trial-requests` — an endpoint **not yet built**. | There is no self sign-up (FR-6.1): we create the school. While the front end is being built first (D-7), the form validates in full and, with no `VITE_API_URL` set, keeps the request in the visitor's browser so the page can be demonstrated end to end. A release build (`BRILLANDA_RELEASE=1`) refuses to produce a site that has no real endpoint, or that still contains sample content. The API module lands in the backend phase. |
| D-13 | The four extra modules (attendance, fees, timetable, messages) are shown as **“Coming soon”**, named in no pricing plan. | They are built immediately after the core six. Saying so on the page is deliberate: the page's honesty is part of the pitch. |
| D-14 | **Outfit is loaded on the sign-in screens only** (2026-09-21), and the app's palette is now the site's: warm paper neutrals, ink primary, ochre accent. | Settles the open question raised in `design/patterns/auth.md` §4; a scoped exception to Guide §6's no-webfonts rule. `AuthLayout` adds one stylesheet link the first time a sign-in screen renders, one weight (500), subset to the glyphs a heading or school name can contain via Google's `text=`: about 8 KB measured. Labels, fields, errors and buttons stay on the system stack, and the screen is legible before the font arrives. To reverse: delete `useDisplayFont` in `AuthLayout.tsx`; the `display` font family falls back to the system stack. Screen rules live in `design/patterns/auth.md`. The wrong-password message is pinned client-side to "That email and password don't match." for every 401; the API's own wording ("Email or password is incorrect.") should be aligned when the backend phase starts. |
| D-7a | **Sample sign-in accounts in development** (2026-09-28): one per portal, password `brillanda` (`admin@greenfield.sample`, `teacher@greenfield.sample`, `parent@greenfield.sample`, `team@brillanda.sample`). | Amends D-7 ("login is real"): with the API not running locally, no portal could be opened. The stand-in answers only for these four emails and passes every other email through to the real API, so real accounts keep working when the backend runs. The sign-in page shows one button per account in development. Browser only (tests supply their own sessions); production builds contain neither the accounts nor the buttons (checked in the built bundle). Delete `mocks/sampleSignIn.ts` and `shared/api/sampleAccounts.ts` once a seeded backend runs locally. |
| D-15 | **The Pastel look, with Outfit throughout** (2026-09-28), chosen from the clickable prototype in `design/prototype`. A school can switch to **Neutral** (black, greys, white). | Supersedes D-14's "sign-in screens only" and the paper, ink and ochre palette of D-9 and `design/patterns/auth.md` §3. Outfit (400, 500, 600) loads from Google Fonts with `display=swap`, so text shows in the system face at once: a deliberate exception to Guide §6's no-webfonts rule, accepted for the brand. Each class level has its own tint (surfaces), deep ink (text on the tint) and mid tone (marks), from a colour-blind-checked set. Status inks pass AA on their own fills, so status text may sit on them (supersedes F-34 for these values). Neutral is kept per device for now (`brillanda:look`); it moves to `School.settings` once school settings have an endpoint. The other prototype looks (Calm, Assembly, Frosted, School colours) stay in the prototype. |
| D-16 | **One shell for every portal**: a floating sidebar on wide screens, a tab bar on phones, and an account menu (look, sign out). | Replaces the teacher portal's bare header (Guide §7, "no sidebar"); the teacher's menu stays at two items, Home and My classes, so it is no busier. Portals whose pages aren't built yet show their full menu, and each page says plainly that it is being built. |
| D-17 | **A demo build for Vercel** (2026-10-02): `VITE_DEMO=true` keeps the stand-in data and the sample sign-in buttons in a production build of `apps/web`, so the deployed app can be shown before the API exists. | Amends D-7 and D-7a ("production builds never use stand-in data") for builds that ask for it by name only. Without the flag, a production build still contains no sample data (checked in the built bundle). Everything a demo visitor does stays in their own browser; nothing is sent anywhere. The "Sample data" badge shows in every demo screen. Site and app deploy as **one Vercel project on one address** (amended 2026-10-02 at the product owner's request): `scripts/build-for-vercel.mjs` builds both and combines them, the site's page at `/` and the app's as `app.html`, which the root `vercel.json` serves for every other path except `/api/` and `/assets/`. The app is built with `VITE_DEMO=true` unless the project sets `VITE_DEMO=false`; set that once the API is deployed. The same `vercel.json` sets a long cache for hashed assets, a week for photos, and basic security headers. |

## Spec fixes

| ID | Problem in the spec | Resolution |
|---|---|---|
| F-1 | Inclusive ranges like 70–100 = A, 60–69 = B leave 69.5 matching no band, so `resolveGrade` throws. Float maths (e.g. 7/20 × 20) can produce 69.9999…. | Grade bands are **thresholds** (`minScore` only): a total gets the highest band it reaches. Every scale must include a band at 0, so gaps are impossible. Totals are rounded to 2 dp before grading. |
| F-2 | Assessment components and grading scales had no session/term, so editing next year's scale would change last year's report cards on regeneration (contradicts Guide §9 and FR-8.6). | Both are **scoped to an academic session**; rollover copies them forward. `Result` rows are frozen while a class is published, and `PublishStatus.configSnapshot` stores the scale/components printed on report cards. |
| F-3 | `Result` is recomputed on every score change, which would silently wipe an admin override (FR-13.5). | `Result.total` is the effective total; `computedTotal` always holds the system value. `isOverridden` + `overrideReason` make recomputation update `computedTotal` only. |
| F-4 | FR-15.1/15.2 track status per class **and subject**, but `PublishStatus` was unique per (class, term), and FR-12.7's unlock request had no model. | New `SubjectEntryStatus` per (arm, subject, term) for not started → in progress → complete → locked, plus `UnlockRequest`. `PublishStatus` stays per (class, term) for publishing. |
| F-5 | Arms were missing from assignments, publish status and ranking, so a JSS 1A teacher would see JSS 1B students. | `armId` added to `TeacherAssignment`, `Enrollment` (required), `SubjectEntryStatus`, `Result`, `TermSummary`. **Every class has at least one arm**; a class without arms gets one default arm named after the class, and the UI hides it. This avoids nullable columns inside unique keys. |
| F-6 | No link from parent accounts to students (portal couldn't find "my children"). | `ParentStudent` join table; `Student.userId` for the STUDENT role login. |
| F-7 | No storage for invite links (72 h), password-reset links, or refresh tokens (needed for FR-22.4 idle expiry and revocation). | `AuthToken` (invite / reset, hashed, single-use) and `RefreshToken` (hashed, `lastUsedAt` for idle timeout). |
| F-8 | No place for the motto (FR-6.4) or school toggles (FR-16.4, FR-23.3, D-1, D-2, D-5). | `School.motto` and `School.settings` (JSON validated against `SchoolSettings` in `@brillanda/shared-types`). |
| F-9 | "Rollover clones classes/subjects into a new session" — but classes and subjects were never session-scoped. | Classes and subjects persist across sessions. Rollover = create session + terms, copy assessment config (F-2), batch-promote students. |
| F-10 | Guide has a `staff` module but no staff table; `User` had no phone. | Staff are `User`s (TEACHER / SCHOOL_ADMIN) with an added `phone`. |
| F-11 | `Student.status` was free text duplicating the enrollment enum; `guardianContact` mixed phone and email. | `Student.status` uses `EnrollmentStatus`. `guardianContact` split into `guardianPhone` and `guardianEmail` (the latter enables parent invites on import). |
| F-12 | `Score.teacherId` is misleading: admins can enter scores too. | Renamed `enteredById`. `Score.isAbsent` added (D-3). |
| F-13 | Ranking needs each student's arm at the time of computation; FR-14.4 allows an admin remark. | `Result` and `TermSummary` store `classId` + `armId`. `TermSummary.average` is null until all class subjects have results; `adminRemark` added. |
| F-14 | FR-20.5 needs audit logs immutable, not just "no edit endpoint". | A database trigger rejects `UPDATE`/`DELETE` on `AuditLog`. The table has no foreign keys, so it never blocks or cascades. |
| F-15 | Invited users have no password yet; code-only parents have no email. | `User.passwordHash` and `User.email` are nullable. |
| F-16 | — | Actor columns (`lockedById`, `publishedById`, `completedById`, `resolvedById`) are plain ids, not foreign keys: users are deactivated, never deleted. |
| F-17 | Guide asks for an explicit `(schoolId)` index on every table. | Omitted where a composite index or unique constraint already starts with `schoolId` (it would be redundant). |
| F-18 | Must-have requirements with no endpoint in Guide §5. | To add in their phases: full data export (FR-19.4), import template download (FR-19.1), unlock requests (FR-12.7), parent access-code login (D-5). |
| F-19 | FR-13.6 says recomputation is "instantaneous"; Guide §8 debounces class-wide positions. | Kept the Guide's approach: each student's subject total/grade is recomputed on every save; class positions are debounced and always refreshed when the Publishing screen opens. |
| F-20 | "Only one active session/term per school" (FR-8.1). | Enforced in the service layer inside a transaction. Partial unique indexes were avoided because Prisma would try to drop them in later migrations. |
| F-21 | Suspending a school (FR-6.5) must cut off users who are already logged in. | Auth middleware checks school status on each request (Phase 1 step 2). |
| F-22 | Scoping queries by `schoolId` does not stop a request from referencing another school's record by id. | Every client-supplied id (student, component, class…) is verified to belong to the caller's school — and, for teachers, to their assignment — and covered by the cross-tenant test suite. |
| F-23 | Guide §1 says "JWT access + refresh token" but not where the refresh token lives or how it is revoked. | **Access token:** HS256 JWT, 15 min, carrying only the user id. Role, status and school are loaded from the database on every request, so deactivation and suspension take effect immediately. **Refresh token:** opaque random value, stored hashed, sent in an `httpOnly`, `SameSite=Strict` cookie limited to `/api/v1/auth` (never readable by JavaScript). Rotated on every use; the old token keeps working for 60 s so tabs refreshing together don't log each other out. A rotated token reused after that is treated as stolen and ends all of the user's sessions. Idle timeout (24 h) and maximum age (30 days) are configurable. `JWT_REFRESH_SECRET` is not needed. |
| F-24 | Guide §3's `withTenant` helper relies on every developer remembering to call it correctly. | `withTenant(schoolId)` is a Prisma client extension: reads, updates and deletes on every model with a `schoolId` column get `schoolId` ANDed into the filter, creates are stamped, and writes naming another school are refused. New models are covered automatically; a test pins the list. Still not covered: ids inside `data`, nested writes, raw SQL (see F-22). |
| F-25 | Login needs brute-force protection, but a whole school often shares one IP address. | Login and forgot-password are rate-limited per IP **and** email (10 / 15 min and 5 / h), with a generous per-IP ceiling (300 / 15 min). Access codes: 50 / 15 min per IP. Counters are in memory, which is fine for one API instance; switch to the Redis store if the API is scaled out. |
| F-26 | Invites are part of auth (Guide §11 step 2) but `POST /users/invite` sits in the users module. | Built now; the rest of the users module comes with staff CRUD in step 4. Inviting someone whose invite is still pending re-sends it with a fresh link and retires the old one. Only TEACHER and SCHOOL_ADMIN can be invited here; parents are invited alongside student records. |
| F-27 | Endpoints the web app needs that Guide §5 doesn't list. | `GET /auth/me`, `POST /auth/logout`, `GET /auth/invite/:token` (shows who the invite is for), `POST /auth/access-code` (D-5). |
| F-28 | Password rules weren't specified. | 8–72 characters (72 bytes is bcrypt's limit), no composition rules, per NIST SP 800-63B: simpler for non-technical users and no weaker in practice. bcrypt cost 12. Reset links last 1 hour, and a reset logs the user out everywhere. |
| F-29 | Guide §10's `scopeToTeacherAssignment` middleware. | Deferred to the scores module (Phase 2), the first place teachers act on class data. |
| F-30 | Guide §5 has no endpoint for the teacher's home screen, and its score routes predate arms (F-5). | Contract in `packages/shared-types/src/teacher.ts`: `GET /teacher/assignments` (active term + the teacher's arm/subject pairs with progress); `GET /scores?armId=&subjectId=&termId=` returns the whole sheet (students, components, grading scale, status); `PUT /scores/:studentId/:componentId` carries `subjectId` and `termId` in the body, because a school-wide component doesn't identify its subject, and `value: null` clears a cell; `POST /scores/arm/:armId/subject/:subjectId/term/:termId/mark-complete`. Web routes: `/teacher` and `/teacher/score-entry/:armId/:subjectId/:termId`. |
| F-31 | Guide §7 specifies `<input type="number">` for score cells. | Text inputs with `inputMode="decimal"`: cells must accept `ABS`, and number inputs change their value on arrow keys and the scroll wheel, which is dangerous in a grid. Up/Down arrows move between rows instead. Follow-up: phones' decimal keypads have no letters, so marking absence on a phone needs its own control. |
| F-32 | Guide §8 puts the computation engine in the API, but the grid must show live totals with identical maths (Guide §7). | Totals, rounding, grade lookup and score parsing live in `packages/shared-types/src/grading.ts` and are used by both the grid and (in Phase 2) the API's `computeResult.ts`, so the two can never disagree. Rounding goes through 12 significant digits to strip float noise (69.995 → 70). |
| F-33 | Autosave on a weak connection (FR-12.4, R-5). | Values commit when a teacher leaves a cell. Saves for one cell are sent one at a time, always with the newest value, so a slow response can't overwrite a later edit. Network failures mark the cell and show a banner. The save is retried when the connection returns, when any other save succeeds, or on "Try again". The browser warns before leaving with unsaved scores. |
| F-34 | Guide §6's warning token (#A9760C) is about 3.6:1 on its tint, below WCAG AA for text (NFR-6). | Status colours are used only for dots, marks and fills; text on tinted backgrounds stays in the primary text colour. |
| F-35 | Guide §6 asks for 1px row dividers; the product owner asked for no heavy lines (D-9). | Added tokens: `--color-divider` (hairline a step lighter than `--color-border`), `--color-field`, `--color-hover`, `--shadow-raised`. Structure comes from spacing, faint fills and one raised surface per view. The row being typed in is tinted. The system font stack is kept (Guide §6 rules out webfonts for low bandwidth). All motion honours `prefers-reduced-motion`. |
| F-36 | The Brillanda team (SUPER_ADMIN) had no endpoints in Guide §5, and the schema has no trial end date and no store for website trial requests. | Contract in `packages/shared-types/src/platform.ts`: `GET /platform/schools`, `POST /platform/schools` (creates the school and invites its admin, optionally from a trial request), `POST /platform/schools/:id/{suspend,restore,extend-trial,plan}`, `GET /platform/trial-requests`, `POST /platform/trial-requests/:id/{book-call,decline}`, `GET /platform/activity` (built from AuditLog across schools), `GET /platform/usage`. Being on trial is the `TRIAL` plan tier, not a status; a school is ACTIVE or SUSPENDED. To add in the backend phase: `School.trialEndsAt`, `School.city`, and a `TrialRequest` table (the website form of D-12 writes to it). Suspending needs a reason and the school name typed to confirm. Served by stand-ins (`mocks/platformHandlers.ts`) until then. |
| F-37 | Guide §5 has no endpoints for the admin dashboard (term overview, class progress, reopen requests, publishing, report card preview, parent invites, school settings). | Contract in `packages/shared-types/src/admin.ts`: `GET /admin/overview`, `GET /admin/arms`, `GET /admin/arms/:armId` (sheets with teachers and reopen requests; students with parent status, and average and position once every subject is complete), `GET /admin/sheets?armId=&subjectId=` (a read-only copy of a sheet), `GET /admin/unlock-requests`, `POST /admin/unlock-requests/:id/{approve,decline}` (approving puts the sheet back IN_PROGRESS), `POST /admin/reminders`, `POST /admin/publish` (only arms whose every sheet is complete; locks them and reports parents emailed and printed slips), `GET /admin/report-cards/:studentId`, `GET /admin/students`, `POST /admin/students/:id/invite-parent`, `GET /admin/staff`, `GET` and `PUT /admin/{school,term,grading-scale}`. Staff invites use the existing `POST /users/invite` (F-26). Totals, grades and positions come from `grading.ts`, so the stand-in and the API agree. The stand-in school (`mocks/schoolDb.ts`, 12 arms and 9 subjects) is separate from the teacher portal's small sample, so a teacher marking a class complete does not yet move the admin's figures; they join up when the API serves both. |
| F-38 | Guide §5 has no endpoints for the parent portal (children, published results by term, report card, "new result" marker, school notices). | Contract in `packages/shared-types/src/parent.ts`: `GET /parent/children` (each child with the latest published term and whether it has been opened), `GET /parent/children/:id/results` (every published term: subjects with each assessment, total, grade and remark, plus average and position in the arm), `GET /parent/children/:id/report-cards/:termId` (the same card the admin previews), `POST /parent/children/:id/terms/:termId/seen` (opening a result clears its "new" marker), `GET /parent/notices`. A parent only ever sees published terms of their own children; the API must check the link, not trust the id. To add in the backend phase: a store for when a parent first opened a result, and a `Notice` table. Served by stand-ins (`mocks/parentHandlers.ts`): last session is fixed sample history, and the current term comes from the admin stand-in once that class is published, so publishing in the admin portal shows up for the parent. |
| F-39 | Build Guide §11 step 3 asks for a setup wizard (school → session and terms → classes and arms → subjects); the Onboarding Flow document says configuration that can be defaulted must never block, and FR-6.1 rules out self sign-up. | The Onboarding Flow wins, adapted to FR-6.1: its steps 1–2 (account, school name) are the Brillanda team's "Create school" (F-36) and the admin accepting the invite. The school is created with defaults (three terms, JSS 1–SS 3 with arms A and B, nine standard subjects, the standard grading scale, CA1 20 / CA2 20 / Exam 60). The admin's first sign-in opens a first run at `/admin/welcome`: the defaults shown, then one class with up to ten pasted names, then the real score grid with a live class ranking. Contract in `packages/shared-types/src/admin.ts`: `GET /admin/setup`, `POST /admin/setup/try-class`, `POST /admin/setup/first-run`, `POST /admin/setup/checklist/{hide,show}`, `POST` and `DELETE /admin/school/logo` (multipart, PNG/JPG/WebP/SVG up to 1 MB). A school admin may save scores through `PUT /scores/...` for their own school. Names from the first run get placeholder admission numbers (`TEMP-001`); trying again replaces them. To add in the backend phase: setup flags on `School` (or derived), and logo storage. Editing classes, arms and subjects comes with the next steps. The demo's "New school (first run)" sample account signs in to Sunrise Academy, which starts afresh at every sign-in. Known simplification: one subject list for every class; real senior classes take different subjects. |
| F-40 | Enrolment (the product owner's "manage the whole school" direction, 2026-10-05) needs endpoints Guide §5 doesn't have, and admission numbers had no rule. | Contract in `packages/shared-types/src/admin.ts`, matching the existing `Student`, `Enrollment` and `EnrollmentStatus` models: `GET /admin/students/:id`, `POST /admin/students` (name and class required; gender, date of birth, join date and guardian optional; can email the guardian an invite), `PUT /admin/students/:id` (a new arm moves the student, with this term's scores), `POST /admin/students/:id/leave` (WITHDRAWN, TRANSFERRED or GRADUATED, with a date and note) and `/readmit`, `GET` and `PUT /admin/admission-numbers`. `GET /admin/students` now includes those who have left, with `status`; they keep their record and results but drop off class lists, score sheets and counts. | F-41 | Build Guide §11 step 4 asks for a CSV import "with a validation report", but not which formats, how columns are matched, or what happens to bad rows. | Two ways in: a CSV file (comma, semicolon or tab), or cells **pasted straight from Excel or Google Sheets**, since most schools keep their lists in Excel; `.xlsx` files themselves are declined with instructions, to avoid shipping a spreadsheet parser. Rows already in the school (same admission number, or same name in the same class without a number) and repeats within the file are problems, so importing the same list twice never enrols anyone twice. Problem rows download as a CSV with a "What to fix" column. Up to 2,000 rows per import. A successful import ticks "Import your full student list" on the setup checklist (F-39). |
| F-42 | Student management (the product owner's priority, 2026-10-05) needs one page per student; the side panel from F-40 only held contact details. | `/admin/students/:id` replaces the panel: a header (photo, class, admission number, age, status, and the edit / move / leave / readmit / invite actions), then Overview (this term subject by subject, average and position once complete, guardian and details), Results (every published term since joining, with a trend chart and each report card), History (class per session, and a timeline of what happened to the record) and Notes (staff only; parents never see them). To add in the backend phase: a `StudentNote` table and a `StudentEvent` log (or derived from AuditLog). | F-43 | FR-8.1 allows one active session and term per school, but nothing said how a term ends or the next begins. | Settings → Session shows the session's three terms (closed, now, upcoming). **Closing a term** (`POST /admin/session/close-term`, with the next term's dates) locks every score, keeps the term's sheets and publishing as they were, and starts the next term with empty sheets for the same classes, subjects and teachers; pending reopen requests are dropped. While classes are unpublished the API refuses (409) unless the admin ticks "close anyway", and those parents never see that term. Closed terms' results stay on each student's page and, where published, in the parent portal. A class closed before every subject was complete is marked **unfinished**: its average covers only the complete subjects, it has no positions, and it is kept off trend charts (`TermResult.unfinished`, staff views only). `GET /admin/session` lists the terms and the unpublished classes. The third term closes through promotion (F-44). To add in the backend phase: a `CLOSED` state on Term and a closedAt date; closed terms' scores already live in Score rows keyed by term. Not yet joined up: the teacher portal's sample data still sits in the first term. |
| F-44 | Promotion at the end of a session: the product owner asked for it to be automatic **and** editable (2026-10-05). | `/admin/session/promotion`, reached from Settings → Session. Each current student's **yearly average** is the average of the session's term averages (unfinished terms count their complete subjects; terms with no results are skipped). Suggested decision: final-year students **graduate**; everyone else **moves up** at or above the pass mark, else **repeats**; a student with no results at all is suggested to move up. The pass mark defaults to the grading scale's lowest pass grade (40) and is editable. Any decision can be changed, with an optional reason; choosing the suggestion again clears the change. The page can be previewed any time, but the session closes only in its last term: `POST /admin/promotion/complete` closes that term (as F-43), moves everyone at once (JSS 1A → JSS 2A, same letter, else the next class's first arm; repeaters stay; graduates get status GRADUATED and leave), records each student's past classes and a timeline entry, and starts the next session's first term with fresh sheets. Contract in `admin.ts`: `GET /admin/promotion`, `PUT /admin/promotion/pass-mark`, `PUT /admin/promotion/students/:id`, `POST /admin/promotion/complete`. Admission numbers then use the new session's year. To add in the backend phase: next session's Enrollment rows are created at completion; the pass mark goes in `School.settings`. Open questions for the school: JSS 3 to SS 1 may depend on the external BECE; for now it follows the same rule and can be changed by hand. |

## Open questions

- **Elective subjects.** The model assumes every student in a class takes every subject assigned to that class. Senior classes (Physics vs Literature) and religious studies (CRS vs IRS) usually break this, and it affects FR-13.3's "average once all subjects are complete". Needs a decision before Phase 2 score entry; the likely fix is an optional per-student subject list.
